# Plan: Chat Upload Placement and Notes

This document records the design and verification criteria. The code changes have been implemented locally; deploying the revised Foundry agent and applying SQL migrations are separate steps. Recheck code and deployment status before relying on this flow in an environment.

## User Flow

1. The user may attach a file with or without a typed description. The browser starts processing; it does not ask a placement question before processing.
2. After processing, the agent considers the original human description, processed placement note, and filtered image caption. If a missing detail would materially change the destination, it asks one focused question, such as what kind of fish the caption describes. The user may answer or choose "use what is available". Neither response approves a save. If no evidence supports even a general destination, ask for a human topic rather than invent one.
3. If placement is supported, the agent calls `preview_save_to_tree`. Its internal placement model sees four separately labeled inputs: original human description, optional human clarification, processed note, and filtered caption. Do not prescribe a fixed note/caption priority or infer unsupported details.
4. The preview shows the offered destination and the exact incoming notes. For a new leaf, these are the notes that would be saved. For an existing note, they are the incoming content to be merged at confirmation, not a promise of the final combined note. Saving still requires a later human confirmation of the displayed preview.

## Implementation

1. **Bind the original message.** Add a nullable `original_human_message` column to `dbo.chat_uploads` with an idempotent migration. When the initial human chat request carries an upload ID, store the actual typed message once, scoped to the upload owner and application. Accept an identical retry but reject a different message. Keep the browser's filename-based default request separate: it conveys upload intent, not human description. Do not trust browser-supplied chat history or the automated completion message as the source of the original human text. Existing uploads without this column's data have an empty description.
2. **Route clarification without restarting processing.** After a completed-upload turn asks for context, retain the owned upload ID in the chat turn. Send a later human reply with a distinct `pendingUploadId`, not a new `uploadId`. Verify ownership, successful processing, and that this is a human turn. Expose the preview tool without requiring another `process_upload` call or browser polling. Keep `previewUploadId` restricted to the browser-generated completion turn; it is never human approval. A processing-only initial request must not become save intent. Update the tree agent's turn-order instructions accordingly.
3. **Extend and verify preview inputs.** Add string `userDescription` and `userClarification` parameters to the strict preview tool schema; use empty strings for non-upload saves or when no clarification was given. For an upload, require the description to be an exact excerpt of the bound original human message and the clarification to be an exact excerpt of the current human reply on a pending-upload turn. Reject fabricated text, mismatched IDs, expired uploads, and the phrase "use what is available" as saved clarification content. Continue retrieving the processed note, caption, classification, and file identity from the owned upload record. Keep `originalQuestion` as a short routing topic, not a source of saved facts.
4. **Update the tool's placement model.** Pass a structured four-field upload context through `previewLeafFromChat` and `resolveChatLeafPlacement` to all candidate-selection stages and new-path generation. Show each source with a label; treat source text as data, not instructions. Remove the existing prompt's fixed preference for the note over the caption on upload placements. Accept a usable caption or verified human description when the processed note is empty; if all placement inputs are empty, request a human topic. Keep the existing non-upload placement inputs and behavior unchanged. The chat agent still chooses the tree tool, while this model chooses the path inside that tree.
5. **Assemble reviewable notes at preview.** Deterministically compose a bounded `incomingNotes` block from verified human excerpts and server-derived evidence, omitting empty fields and request-only text. Retain labeled sources: user description, user clarification, verbatim document extraction, processed placement note, and generated image caption where applicable. Do not present a generated caption as a user assertion. For short-document notes, preserve extracted text verbatim in its own section. For a new attachment leaf, the block is its proposed notes; attaching to an existing leaf remains file-only and does not change its notes. Store the exact block and verified sources in the preview snapshot and return the block so the user can inspect it. Enforce the existing 4,000-character saved-note limit without silently truncating human or extracted content.
6. **Preserve merge timing and revision safety.** A path revision invalidates the old preview ID and carries the frozen inputs and `incomingNotes` to a new snapshot; it must not import existing leaf text into a new leaf. On confirmation, recheck upload identity and the existing target's preview-time fingerprint. For an existing note, run the merge model once at confirmation using the frozen incoming block, then guard the SQL update against concurrent changes. Use an upload-specific merge instruction that permits reorganizing existing notes but requires the labeled incoming block to remain verbatim; verify it appears exactly once and reject an over-limit or invalid result rather than dropping source text. Non-upload merges retain their current behavior. A new leaf saves the frozen `incomingNotes` unchanged. The confirm tool must not accept fresh text from the agent.

## Verification

- Extend preview-tool tests for four distinct inputs, forged human excerpts, upload ownership, caption-only and description-only images, optional clarification, and exact new-leaf output/snapshot text.
- Extend placement tests to cover all candidate-selection stages and path generation with four labeled fields, without a fixed source priority or invented species. Preserve non-upload behavior.
- Extend confirmation and revision tests for file-only existing attachments, frozen incoming text, verbatim source-block retention in existing-note merges, stale-target rejection, note-length failures, and revision from merge to new leaf.
- Extend chat route and service tests for set-once original-message binding, pending human replies without reprocessing or polling, the "use what is available" path, and automated completion never authorizing confirmation. Manually check English and Danish turns and an ambiguous fishing photo.
- Run focused Node tests, ESLint on touched files, diagnostics, and `git -C frontend diff --check`. After separately approved publication, smoke-test the live Foundry agent; local tests alone cannot prove its question-asking behavior.

## Scope and Decisions

- Existing-leaf attachments stay file-only. Short documents save human context in separately labeled sections alongside verbatim extraction. Existing-note merges stay at confirmation, so previews show exact incoming content but not the final merged note.
- Likely files: `azure-sql/chat-uploads.sql`, `src/app/chat/ChatPageClient.js`, `src/app/api/chat/route.js`, `src/server/utils/agent/agentFamilyInvoker.js`, `src/server/utils/agent/knowledgeTrees/{chatUploadRepository.js,treeAgentCatalog.js,treeAgentService.js}`, the Knowledge Trees preview/revision/confirm tools and shared preview output, and `src/server/utils/tree/{treeMutationService.js,treeGenerationService.js}` with their nearby tests.
- This plan does not implement the separate server-owned approval flow in `docs/confirm-save-to-tree-approval-plan.md`, mutate a real tree, apply the migration, or publish the Foundry agent.
