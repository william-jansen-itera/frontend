# Plan: Server-Owned Approval for Tree Saves

This document records the intended change; it is not an implementation. Recheck the code before starting work.

## User Flow

1. A user accepts the offer to save a broad answer in conversation. That permits `preview_save_to_tree` to produce a preview, but does not authorize a write.
2. The app shows the preview's offered destinations and a server-generated Approve/Cancel control. The next approval is a click, not a second typed confirmation or another model turn. If both merge and create are offered, the user selects the save mode in the approval UI before clicking Approve.
3. The user can revise the destination in chat while an approval is pending or after clicking Cancel, until the preview expires. Revision invalidates the old preview and any pending approval, then issues a new preview ID and approval. Cancel declines only the approval: the preview remains revisable, but the cancelled approval cannot be reused. Saving the unchanged preview after cancellation would require an explicit new authenticated approval operation, not revival of the cancelled ID.
4. A mode change keeps the preview but replaces its approval. Only the currently approved preview version and mode may be saved. Independently created previews must not invalidate one another.

## Implementation

1. **SQL storage and transitions.** Add a forward-only migration under `frontend/azure-sql/` for principal- and application-scoped tree previews, keyed by an opaque ID and holding the full immutable snapshot, expiry, and current/superseded/consumed state. Keep the existing 30-minute preview lifetime distinct from the five-minute approval lifetime. Extend `dbo.agent_action_approvals` to link a tree preview and support supersession without changing email approval behavior. Use SQL transactions for preview revision, mode-selection approval rotation, and approval claim: the claim must verify principal, current preview version, offered mode, and both expiries before consuming the preview and claiming the approval. Cancellation declines only the approval. Do not accept client-authored paths, note text, tree IDs, or snapshots as authority.
2. **Preview tools and policy.** Move `treePreviewSnapshotRepository.js`, `previewAddToTreeTool/index.js`, and `reviseTreePreviewTool/index.js` from personal-cache snapshots to SQL while retaining the existing preview tool output. After a valid final preview response, create a pending approval from the latest server-side snapshot and its default offered mode; return approval data alongside the ordinary preview answer and family/debug payload. Set `confirm_save_to_tree`'s server policy to `requiresUserApproval: true`. Update its handler so a model invocation without a trusted, server-supplied approved snapshot cannot mutate a tree. The server route executes the approved save. Update tree agent instructions and tool description so the model previews/revises but does not request another conversational confirmation or autonomously save. Publishing revised agent instructions is a separate deployment step.
3. **Approval dispatch and outcome.** Extend `/api/chat/approval` to dispatch tree approvals as well as email approvals, retaining authentication and origin checks. A tree approval service verifies family, tool, policy, selected mode, and claimed snapshot, rechecks writable-tree access and relevant save preconditions, then calls the guarded confirm handler. Record the actual result or failed/uncertain outcome; never automatically retry an uncertain write. Cancel does not invoke a tree mutation. The preview response has already finished, so return a server-authored tree result with the actual saved notes, path, link, and classification rather than attempting to resume a nonexistent pending Foundry tool call. Any optional model wording turn must have no write tools and a server-authored fallback.
4. **Chat UI.** Show the tree name, exact offered path(s), selected mode, and a concise server-generated note-content preview. Mode selection rotates the pending approval ID; stale IDs fail. Keep the tree composer available for revisions while approval is pending or after cancellation, without changing the existing email approval behavior. Replace or hide stale controls after revision. Handle cancellation, expiry, failure, replay, and concurrent clicks distinctly. Do not label tree approvals as email deletion or log full private note text.

## Verification

- Use synthetic tests for: no leaf write on preview, revision, or cancel; cancellation leaves the preview revisable but its approval unusable; revision supersedes the old preview and approval; mode selection replaces only the approval; wrong principal, expiry, stale revisions, replay, and concurrent clicks fail closed.
- Check that a model call without trusted approval cannot save, that an approved save uses only the immutable SQL snapshot once, that writable-tree access is rechecked, and that create/merge return actual notes, path, and link even if response shaping later fails.
- Run focused `node --test` checks, `npm run lint`, and `npm run build` in `frontend`. Apply the SQL migration before deploying code, but not during automated tests. Do not mutate a real tree or publish Foundry agents as part of verification; a disposable-tree manual check needs explicit permission.

## Scope

Expected files: a new SQL migration; `src/server/utils/agent/agentActionApprovalRepository.js`; the knowledge-tree preview, revision, confirm, catalog, service, and result-builder modules; `src/app/api/chat/approval/route.js`; `src/app/chat/ChatPageClient.js`; and relevant chat locale resources. Reuse existing approval infrastructure. Do not modify the generic execution loop unless a focused failing test shows it is necessary. Email approvals and unrelated tools are out of scope.
